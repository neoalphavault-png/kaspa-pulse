Does Kaspa have smart contracts? Yes, since the Toccata hard fork.

"Kaspa has no smart contracts" was true for years, and repeating it today marks you as out of date. Contracts run in two places on Kaspa today, built two very different ways. Here's the full stack, in plain language.
The short answer

Yes, Kaspa has smart contracts. Since the Toccata hard fork, Kaspa's layer 1 runs native covenant contracts, spending rules that sit inside the coins themselves. The developer documentation at docs.kaspa.org puts it in two sentences, "Toccata makes Kaspa UTXOs expressive enough to carry real application state. It is active on mainnet as of June 30, 2026, at DAA score 474_165_565."

On layer 1, 18,006 covenant outputs were unspent on chain at the end of 25 October 2026, source kaspalytics, logged daily in our covenant log. On top of layer 1, two EVM layer 2s, Kasplex and Igra, run contracts written for the EVM, with the capital committed to them shown below.

The stack, from bottom to top

Kaspa's answer to smart contracts is unusual because it refuses the standard shortcut. Most chains bolt a single global virtual machine onto their base layer. Kaspa instead built three distinct levels, each with its own job.

Layer 1 covenants, contracts that sit inside coins

Kaspa's base layer is a UTXO chain, like Bitcoin. A covenant is a programmable spending rule attached to a UTXO. The coin itself carries code plus a piece of state, committed on chain as a hash. Whoever wants to spend that coin must reveal the code and state, and the network verifies that the spend follows the rules. There is no global computer executing everyone's programs. Each contract is a small, self-contained state machine partitioned across UTXOs, which is why covenant apps inherit layer 1's speed and parallelism instead of competing for one shared engine.

What covenants do not yet come with is an agreed way to build tokens on top of them. That work is happening in a separate set of proposals, and as of August 2026 none of them is finished. We track where that stands on Kaspa's token standards.

Argent, the language that makes covenants writable

Raw covenant scripting is unforgiving, one wrong byte and funds are stuck. Argent is the high-level language built to fix that. Developers define actors (a contract plus the state it owns), entries (the operations you can call), and transition rules, and the compiler generates the underlying script. Two design choices matter for non-developers too. Every app is a closed system under one covenant ID, so outside code cannot inject itself into an app's state machine. And the compiler is only needed at build time; creating transactions afterwards needs only a lightweight runtime, so tooling in other languages can drive the same apps. Core developer Michael Sutton documents the whole workflow in public coding sessions on the Kaspa Native channel. Episode one builds a working ticketing app from scratch.

Layer 2, full EVM and familiar tooling

For everything built for the EVM, Solidity contracts, MetaMask and existing DeFi codebases, Kaspa has two EVM layer 2s that settle against layer 1, Kasplex, a zkEVM running since 2025, and Igra, running since 2026. This is where Kaspa's DeFi actually operates today, and where the TVL shown above sits. The trade-off is the standard one, EVM compatibility and rich tooling, in exchange for each L2's own performance and trust profile.

Account-based contracts and UTXO contracts

There are two ways to build smart contracts on a blockchain. In an account-based design, contracts are accounts with balances and storage inside one shared machine, and every transaction updates that global state in turn. In a UTXO design, there is no shared machine. Each coin carries its own rules and its own piece of state, and a transaction proves that the next output follows those rules. Kaspa's developer documentation is explicit about which one Toccata built, "The result is still UTXO-native. Toccata does not turn Kaspa into an account-chain smart contract system. Instead it makes UTXOs able to carry state, split into parallel lineages, merge when necessary, and prove the next step." (docs.kaspa.org, read on 6 October 2026)

Neither approach is free. One shared machine makes composability easy and congestion structural. Kaspa's partitioned model keeps the base layer fast and parallel, but asks developers to learn a genuinely different way of building, which is why the tooling work around covenants matters as much as the protocol itself.

Three traps in reading "kaspa smart contracts"

1. The old answer still circulates

Years of "Kaspa is payments only, no smart contracts" left a deep imprint. You will still hear it from commentators and see it in older articles. It stopped being true on June 30, 2026. Anyone repeating it today is describing a chain that no longer exists, so check the activation date, not the vibes.

2. "EVM on Kaspa" is not "Kaspa speed for EVM"

The layer 2s are their own systems. They inherit settlement from Kaspa's layer 1, but their throughput, latency and trust assumptions are their own. When you see EVM performance claims, ask which layer they describe. The honest answer is almost never "layer 1."

3. Young contracts are unaudited contracts

The first wave of covenant apps and L2 protocols is weeks-to-months old. Some launched anonymous, some unaudited, and the standard advice from Kaspa's own core contributors is blunt. Know what you buy. A working demo is not a security review. The mechanism being sound says nothing about any individual app being safe.

Questions people ask

Does Kaspa have smart contracts?

Yes, in two layers. Since the Toccata hard fork on June 30, 2026, Kaspa's layer 1 runs native covenant contracts, programmable spending rules living inside UTXOs, written in the Argent language. In addition, two EVM layer 2s, Kasplex (since 2025) and Igra (since 2026), run full EVM smart contracts on top of Kaspa.

What are Kaspa covenants?

Covenants are programmable spending rules attached to individual UTXOs on Kaspa's layer 1. Each contract is a small self-contained state machine. The coin carries code plus state committed as a hash, and any spend must reveal and satisfy those rules. There is no single global virtual machine. State is partitioned across UTXOs, preserving layer 1's speed and parallelism.

What is Argent on Kaspa?

Argent is the high-level language for writing covenant applications on Kaspa's layer 1. Developers define actors (a contract plus its state) and entries (callable operations), and the compiler generates the underlying script. Each app is a closed system under one covenant ID, and transactions can be created with a lightweight runtime without the compiler.

Are Kaspa smart contracts EVM compatible?

Layer 1 covenants are not EVM compatible, they use a different, UTXO-native model. Full EVM compatibility sits on Kaspa's layer 2s, Kasplex, a zkEVM running since 2025, and Igra, running since 2026, which run Solidity contracts and standard EVM tooling.

Are smart contracts on Kaspa safe to use?

The mechanisms are active on mainnet, but the first wave of applications launched in 2025 and 2026 and much of it is young, some of it anonymous or unaudited. Kaspa's own core contributors advise users to understand exactly what they are buying. Treat individual apps as carrying real contract risk until independently audited.

What did the Toccata hard fork actually add?

Toccata activated on Kaspa mainnet on June 30, 2026 at DAA score 474,165,565. It added covenant rules, covenant IDs, transaction introspection opcodes and zero-knowledge proof verification to layer 1. It did not add account-based smart contracts. Kaspa's own documentation states that Toccata does not turn Kaspa into an account-chain smart contract system. Full EVM contracts run on the layer 2s, Kasplex and Igra.
